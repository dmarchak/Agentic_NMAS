# W5: Lab 9's last step, a ZTP device's heartbeat in Loki

**For the operator, written 2026-10-19 (UTC); Core 1.0's K1** (the operator, 2026-10-18: "Lab 9's
last step: a ZTP device's heartbeat arriving in Loki, run for real on the host").

**Why a sitting:** Create and Verify are confirms, and a confirm needs a verified person
(CLAUDE.md). So you press them in Mercury's v2 interface, in your browser. The agent runs the
two lab steps, starting and destroying the throwaway, each on your word, and reads Loki.

**What it shows** (P6_ZTP.md section 6):
- Lab 8: a configless node is leased an address from a reservation the tool wrote, fetches its
  bootstrap from the tool (a reveal row with the hash), and is reached with the staged
  credential.
- Lab 9: phase 2 sends the network's monitoring profile, whose syslog block carries the
  `NMAS-HEARTBEAT` applet, **and the heartbeat then arrives in Loki.** That last step was never
  shown on a ZTP device: the throwaway network of 2026-10-05 had no profile (C488).

**What is new since W4:**
- The network **Lab 9 run** inherits Default's settings and has no profile of its own, so its
  devices take Default's profile (K11, `profile.read_for`). The Profile page says so.
- The ZTP responder serves every network's reservations (C1252).
- Lab 9 run inherits Default's Kea, so its reservation is written in Default's fragment as
  before.

**The device:** the throwaway C8000v of `docs/bootstrap-probe/nmas-throwaway.clab.yml` (node
`tw-ztp-a`), named **l9** in Mercury. It is the same container W4 used for s5 and s6.

**The values:**

| Field | Value |
|---|---|
| Network | `Lab 9 run` (new, inheriting Default) |
| Name | `l9` |
| Platform | `cisco-ios-xe` |

| Address from | ZTP (the tool reserves it and serves the config) |
| Management address, Mask | `10.255.0.60`, `255.255.255.0` |
| MAC address | `aa:bb:cc:00:02:60` (the throwaway's Gi2, fixed by its topology file) |
| Management interface | `GigabitEthernet2` |

| Domain | `rcn.lab` |

**Rules for the sitting:**
- Nothing in 08:30 to 09:10 UTC.
- Nothing on s3.
- No Default device is changed: every confirm names l9 or Lab 9 run. If a preview names any
  other device, press **Cancel** and stop.
- l9 is never reloaded by Mercury, so no planned-restart window is needed. The lab steps start
  and destroy a node that is not a managed device at that moment.
- Write every time down in UTC.

## Steps

1. **`/v2/settings`, the scope bar's Choose a network, then New network….** Type `Lab 9 run`,
   then press **Preview**, then **Create Lab 9 run**.
   - PASS: "Created Lab 9 run". The network inherits from Default (the default mode).
2. **`/v2/monitoring/profile?list=Lab%209%20run`.**
   - PASS: the notice "Lab 9 run has no profile of its own, so its devices take Default's,
     below, as it inherits Default's settings. Propose one to give it its own."
   - PASS: the rows are Default's sections, syslog among them.
   - **Screenshot.**
3. **`/v2/devices?list=Lab%209%20run`, then Add device….** Fill in the values above, then
   **Review the plan**.
   - PASS: "Create l9 in Lab 9 run: … Nothing reaches a device", with every gate passing.
   - If it lists reasons l9 cannot be onboarded, paste them and stop: nothing was created.
4. **Press Create l9 once.** Write down the time.
   - PASS, amber: "l9 is created and PENDING, not onboarded", with the reservation line
     `aa:bb:cc:00:02:60 -> 10.255.0.60`.
   - Press **Open l9's page**. PASS: ZTP "reserved not leased".
5. **Lab step L1, the agent's, on your word: say "L1".** On `<lab-host>` the agent runs
   THROWAWAY_SESSION.md's Part 1.2 only:

       cd <home>/labs/throwaway && sudo containerlab deploy -t nmas-throwaway.clab.yml

   - It reads back the launch script's hash and the three `CONFIGLESS` lines (W4 step 11), then
     answers "L1 done" with the time.
   - The node takes about 8 minutes to boot and fetch.
6. **l9's page: reload it each minute** until the stage reads **"fetched not reached"**, then
   until the header says it answers. Write down each time.
   - Stop if the stage stays "reserved not leased" or "leased not fetched" 15 minutes after L1
     (the pending page's own rule: "No fetch 15 minutes after boot: stop"), and paste the
     stage line.
7. **Press Verify….** Its preview reaches l9 and sends nothing.
   - PASS: "Verify l9: it answered at `10.255.0.60`. Phase 2 will rotate its bootstrap
     credential, remove … read-write community line(s), **apply the monitoring profile** …".
   - PASS: the profile's program lists the syslog section, with `event manager applet
     NMAS-HEARTBEAT`.
   - **Screenshot.**
   - If it says the monitoring profile does not apply, paste its words and stop: K11's
     inheritance did not reach Verify.
8. **Press Verify l9 once.** Write down the time.
   - PASS: the stepper reaches Promoted, with "Profile sent" done.
   - PASS: "l9 is onboarded: reached at `10.255.0.60` …".
   - **Screenshot.**
9. **The agent reads Loki (read-only), on your word: say "Loki".** It asks Loki for l9's
   `NMAS-HEARTBEAT` lines through the heartbeat check's own reader (`loki_arrivals`) and prints:
   - each arrival's time;
   - the gaps between arrivals;
   - the stream's labels.
   It names how many arrived since step 8's time. The first one is due within one heartbeat
   interval of the profile landing (300 s by the device's clock; C8000v clocks run at about 1.0).
   - PASS: at least two arrivals, about 300 s apart.
   - **This is Lab 9's last step, shown.**
   - The agent also reads Mercury's own Logs for l9 (`/v2/logs?list=Lab%209%20run`, the device's
     Logs tab), so the same lines are seen in the screen the lab uses.
10. **Your choice: keep l9 for your rehearsal, or clear it.** To clear it:
    - **Retire…** on l9's page;
    - lab step **L3** (the agent's, on your word:
      `sudo containerlab destroy -t nmas-throwaway.clab.yml`);
    - Settings › Lab 9 run › **Delete network…**.
    - NetBox keeps what Verify created, as after W4 (C1097).

# Mercury against industry practice: a gap analysis (for the operator's decision)

The operator, 2026-10-07: Mercury should follow proven industry practice. This is a GAP
ANALYSIS, not a rewrite: it maps what Mercury is onto a published reference, says where it
aligns, where it differs and why, and where it should consider shifting, with a recommended
order. **Stage 7's cutover finishes on the current architecture meanwhile; nothing here
changes it mid-flight.**

## 1. The reference

The Network Automation Forum's **Network Automation Framework** names six blocks:
- **Intent** (the source of truth for what the network should be);
- **Executor** (makes changes on devices);
- **Collector** (gathers operational state);
- **Observability** (stores, analyses and alerts on it);
- **Orchestration** (coordinates workflows across the others);
- **Presentation** (the interfaces people and other systems use).

Each block is judged: **ALIGNED**, **DIFFERENT BUT JUSTIFIED** (with why), or **CONSIDER
SHIFTING**.

## 3. The shifts, evaluated

Each shift is judged on what changes, what it unblocks, its risks and its cost.

### (a) NetBox as the source of truth for identity, then design data

- **What changes:** [NSOT_OWNERSHIP](NSOT_OWNERSHIP.md) part 4. Phase 1 makes identity
  NetBox's, with the inventory read from NetBox. Phase 2 moves design data, with intent
  generated from NetBox. Phase 3 turns discovery into proposals for approval. Writes happen
  only as the first step of a confirmed operation, in a NetBox Branching branch.
- **Unblocks:** the drain runbook's status, onboarding from Planned, retire's Decommissioning,
  fleet scale without a CSV, and other tools reading one inventory.
- **Risks:** NetBox becomes a dependency of every operation. An unreadable NetBox keeps the
  last good inventory, dated, and refuses writes. A wrong NetBox record becomes a wrong
  operation, which is why the census comes first.
- **Cost:** Phase 1 is small (the inventory adapter exists). Phase 2 is large (generation, a
  branching spike, migrating intent).

### (b) Merge-only against full-configuration replace

The practice: replace the whole configuration with a candidate, see the platform's own diff
first (a dry run), and roll back automatically unless confirmed:
- IOS and IOS-XE: `configure replace` with the archive feature, `list` for the commands it
  would send, and `time <s>` / `configure confirm` for an automatic rollback;
- NAPALM: `load_replace_candidate`, `compare_config`, `commit_config` and `rollback`;
- EOS and IOS XR: configuration sessions;
- Junos: `commit confirmed`.

**What it takes here:**
- **Intent fidelity per device.** The candidate is the rendered intent PLUS the device's own
  sections intent does not model (certificates, keys, licence lines). Mercury already reports
  the unmodeled lines (seed, the intent editor's acknowledged block, `roundtrip`).
- **A measurement that doubles as the fidelity metric:** for each device, `configure replace
  <rendered candidate> list` against its running config must list nothing when the device is
  at intent.
- **Platform behaviour:** IOS-XE supports `configure replace` with archive. Classic IOS 15
  (vIOS) supports it too; vIOS-L2 is to be measured.

**What changes if adopted, per device, once its fidelity is measured:**
- **Removal shapes become unnecessary for most lines.** The platform computes its own
  negations, which is the "ask the platform" principle of Mode B, applied whole.
- **Revert becomes one action:** replace with the previous golden. C531 part 2 simplifies.
- **Verify stays,** and the rollback timer adds a safety net when the management path breaks.

**Risks:**
- a candidate missing a device-owned line removes it;
- a replace that touches the management path depends on the timer;
- vIOS-L2's behaviour is unmeasured.

**Recommendation:** merge-only stays the default. After cutover, a spike measures `configure
replace … list` on r2 and s1 against their goldens. A device then EARNS replace eligibility by
measurement, as a baseline is earned, never by a setting.

### (c) Pre-change validation and operational tests

- **Batfish** models the network from configurations and answers reachability, routing and
  ACL questions about a CANDIDATE before it is deployed. It complements C506's declared
  expected effects with a computed answer, and it fits P.10 (validation before production, in
  layers), which is already scoped. Cost: a service to run, and parsing coverage of these
  platforms to confirm.
- **pyATS / Genie:** structured parsers for show commands, and pre/post snapshots with a
  diff. Mercury's verify reads and parses its own outputs; Genie's parsers could replace
  custom parsing in `verify_checks` and the readers. Cost: a dependency (licence and
  air-gapped install to check).
- **SuzieQ:** a normalised operational-state store with assertions. It overlaps Mercury's
  readers; it is worth evaluating against P.16, not adopting beside it.
- **Recommendation:** after cutover, Genie's parsers as a library for verify (measured on
  this estate's show outputs), and Batfish as an optional layer in P.10.

### (d) Configuration generated from NetBox data

- Mercury already renders intent through approved templates and compares the device with it
  (golden, intent match), which is Nautobot Golden Config's backup, intended and compliance
  trio.
- For NetBox-owned fields (Phase 2), Mercury GENERATES `host_vars` from NetBox's data and keeps
  its own approved templates and hashing. NetBox's config templates are an alternative
  renderer, not adopted: Mercury's approval, preview and confirm need its own render.
- **Recommendation:** with Phase 2, not before.

### (e) Orchestration

- P.22 Runbooks (decided): ordered, vetted steps on the pipeline, change sets, revert as one,
  the measured state as the verification step.
- NetBox Event Rules start planning (a preview for a person), never an apply.
- P.16 evaluates the machinery (Temporal, AWX, Rundeck, Celery or RQ, or keeping systemd)
  for queueing and surviving a restart. The operations stay Mercury's.

### (f) Other gaps the mapping surfaces

- **API-first Presentation:** every operation (preview, confirm, status) as a documented,
  versioned API behind the same route gates, verified identity and hash-bound confirm. The v2
  pages become one client of it; ChatOps and the Stage 8 agent become others.
- **ITSM and change tickets:** a change-ticket reference carried in the confirm, recorded in
  the receipt and the commit's trailers, and a status update to the ticket system. An
  optional integration, off unless configured.
- **Change windows:** the planned-restart windows generalise to change windows a runbook
  checks before acting.

## 4. Recommended order

| When | What | Why |
|---|---|---|
| **Before cutover** | nothing new; finish Stage 7, with the queued fixes (C553, C555, C557, C558, C531 part 1's measurements) | no rewrites mid-flight |
| **After cutover, first** | Phase 1 (identity from NetBox), then P.22 Runbooks with Event Rules starting planning | they unblock the drain runbook, onboarding from Planned and retire's Decommissioning; small, on existing pieces |
| **Then** | the `configure replace` spike and the per-device fidelity metric; Genie's parsers in verify | evidence before any executor change |
| **Then** | the NetBox Branching spike, then Phase 2 (design data generated from NetBox) | the largest change, after its spike |
| **Then** | API-first Presentation and ITSM hooks; Batfish in P.10 | they build on stable operations |
| **Later** | Phase 3 (discovery as proposals) | needs Phase 2's ownership |
| **Stays** | the preview, confirm by hash, verify, rollback and record lifecycle; measured removals until replace is earned; receipts and records; template approval; masked secrets; intent in git | the parts already ahead of common practice |

## How a session picks its work (never wait, never run dry)

1. If latest.md names an item in progress, finish it.
2. Otherwise take the first item, top to bottom, that is not DONE or BLOCKED.
3. **When an item needs the operator:** add the question to `docs/handoff/OPERATOR.md` (what is
   asked, the options, your recommendation, the file to open; 6 lines max), mark the item
   `BLOCKED → OPERATOR.md#<anchor>` here, and move straight to the next item. Never stop or wait for
   an answer. Check OPERATOR.md at the start of each session for answers and unblock those items.
4. Mark each item DONE here with its commit sha when it lands.
5. Stage 6 never runs out, so a session never ends because it ran out of work.
6. Build only what this plan or a register row asks for. Don't invent features.

## Rules (unchanged)

- Tests are never weakened, skipped or deleted to get a pass. Retiring a test of behaviour the
  operator removed needs a record of that decision, a Test-Weakened trailer and a registered row.
- One full suite before any deploy. Deploy only when it is fully green, only through nmas-deploy,
  never 02:30–03:30 Denver. Commits on the device-write path get their device-write review first.
  Log each deploy (sha, time, result) in the day's report. If nmas-deploy's own checks fail, use its
  rollback and record it.
- Protected guards (ci.yml, ratchet lists, hooks, settings.json, nmas-deploy, nmas-gate) need the
  operator's exact words. Don't use --no-verify. Never read or print secrets or .env files.
- The AI never touches a device directly. Reads (show, ping, traceroute and the rest of a person's
  read-only tools) are never gated. Only device changes need approval.
- Don't add steps, gates or safety measures the operator didn't ask for.
- Sessions keep working until 02:30 Denver and end their turn only then (the operator,
  2026-11-24), never to report, summarise or ask; progress goes in the report file, not in chat.

# Onboard a device

Onboarding brings a NEW device into the tool in two phases. Create sends nothing to any device: it stages a one-time credential, commits the device's bootstrap intent and makes a bootstrap configuration to boot it with. Verify then reaches the device, replaces that credential, cleans it up, saves it, records its first golden and adds it to the inventory. A device the tool did not build is adopted instead (see [Adopt a device](adopt)).

![The onboarding flow: Create stages a credential and commits a bootstrap with nothing sent; the device boots on that bootstrap config (static, DHCP, or served by the tool through ZTP); Verify reaches it, rotates its credential, saves it and records its first golden, then promotes it; seeding and deploys follow.](diagrams/onboard.svg)

IOS-XE and classic IOS can both be onboarded with a static address or a DHCP reservation; the plan refuses no platform. Classic IOS's bootstrap was measured on a throwaway emulated switch: the line that generates its SSH key, now the last before `ip ssh version 2`, waited 39.5 s and every line landed. ZTP is built and measured on IOS-XE only (below).

## Phase one: Create (nothing is sent to any device)

On Devices, **Add device…** (in the network the top bar names): the device's name, platform and role, how it gets its address (Address from: static, a DHCP reservation, or ZTP, where the tool writes the reservation and serves the configuration on first boot), its management address and mask (for ZTP, the address the tool reserves), its MAC address (DHCP and ZTP), the management interface the tool will reach it on, its gateway (optional: blank when this host is on the device's subnet; behind a relay, the relay's own address), for ZTP its **Route option (3)** (**None (D4)**, the default, or **The relay's own address**, behind a relay only: see [ZTP behind a relay](#ztp-behind-a-relay)), an optional platform management port, and the DNS domain. **Review the plan** shows the plan and the bootstrap configuration with a placeholder password in place of the real one; the plan refuses at once anything that would fail later, every reason together. Create builds the plan again from the form, holding the device's name, and refuses if it no longer passes, or if it is not the plan you reviewed: the review's fingerprint covers the plan and the intent it commits, and a refusal names each value that moved, previewed and now. The review's button is **Create <device>**. It needs a verified person. Then, in order:

1. **Credentials** (`credentials`). Read: nothing. Sent: nothing. Recorded: a generated 24-character one-time password, staged encrypted in the list's repository folder (never committed), and then stored as the device's credential override in the credential store, keyed on its management address (the reserved address, for DHCP and ZTP), for the account `admin`. Staged first, so a crash between the two leaves something that can be recovered. The staged copy stays until Verify or Abandon clears it, and Needs attention says so under What was checked (job health's `onboarding-staged` reading), never as a rotation that was not recorded: it tells the two apart by the device being pending in the manifest and the staged value being the one the credential store holds for it. A Verify whose rotation died between its push and its record leaves a different value staged, and that one is the rotation's row.
2. **Commit** (`commit`). Read: nothing. Sent: nothing. Recorded: the device in the list's manifest, marked PENDING (its name, platform, role, address source, MAC and reserved address), and its initial intent: the bootstrap parameters (address, mask, interface, gateway, domain, platform, address source, MAC) and the network's syslog block, committed as you with `Source: onboarding`. The device is now known to the tool and not in the inventory, so nothing polls it, backs it up or offers it in bulk actions.
3. **Reserve** (`reserve`, ZTP only). The Kea is the one the network owns, as on the DHCP page ([Whose Kea](dhcp#whose-kea)): Default's for a network that inherits Kea, its own for a network that sets one. Read: that Kea's running configuration and leases, to check again that the MAC and address are free and that no route or resolver option would reach the device (behind a relay, but the reservation's own option 3 when it was chosen, still the relay's own address). Sent: nothing to the device. Recorded: the DHCP reservation, in the fragment file the tool owns in that Kea's configuration (behind a relay, the relayed subnet's own reservations file, which is onboarding's alone): the file is written as a candidate, tested with Kea's own configuration test, swapped in, Kea is told to reload, and the reservation is read back from the running server. Then, holding the fragment again after the last write, its record: `dhcp/ztp-reservations.yml` (every reservation in the fragment and in each relayed ZTP subnet's file: MAC, address, hostname, server and file, and for a relayed one its subnet and any option 3) committed as you with `Source: dhcp` in the Kea owner's repository, the same history as the DHCP page's changes, with a `From-Network:` trailer naming your network when it only inherits Kea (`ztp: <device> reserved <MAC> -> <address>`). A record that fails to commit undoes nothing: the reservation stays in Kea, and Create's result says the record was not committed and why, never drawn as done; the next ZTP reservation change on that Kea commits the whole fragment and so catches the record up. The reservation is last among the steps that can fail, because it is what the device will see.
4. **Render** (`render`). Read: nothing. Sent: nothing. Recorded: nothing: the bootstrap configuration is never stored. It is rendered again whenever it is needed, from the committed intent and the staged credential, so it exists exactly while that credential does.

A failure stops the run, says which step and why, and leaves only what the tool wrote; Abandon removes it.

### A device NetBox already holds {#netbox-planned}

The plan reads NetBox for the name. A record whose status is **Planned** is the device's own: a person made it there for this device, and onboarding reads it with its site, role, platform and tags, and its config context, so the environment's own lines and the interfaces NetBox marks management-only shape the bootstrap configuration. The review's NetBox row names what was read. NetBox owns the record's platform and role, so a Planned record that names a platform different from the form's, or a role whose `mercury_kind` is a different kind, is refused naming both: choose its platform or kind on the form, or change the record in NetBox. A role with no `mercury_kind`, or a record with no platform, is said and the form's choice stands. A record with any other status is refused, naming the status and the record's NetBox address: set it to Planned in NetBox (the device's Edit, Status), or choose another name. A name NetBox does not hold is onboarded as before, and Verify's NetBox step creates its record.

## Between the phases: the device boots

The device must boot with its bootstrap configuration. That configuration is the minimum that makes the device reachable: its hostname, the `admin` account with the one-time password (privilege 15), the domain name, the management interface's address (or `ip address dhcp`) and SSH-only login on the vty lines. How it gets onto the device depends on the address method, and only ZTP does it without a person.

A pending device can be abandoned at any time: nothing the tool did has reached it, so abandoning removes only what the tool wrote (the reservation first, for ZTP, then the intent, NetBox's records of it, the staged credential, the SSH host key it kept for the device's address, and the name). The reservation is removed from the Kea the network owns, and its removal recorded in the owner's repository as the reserve step records the write (`ztp: <device>'s reservation removed (<MAC>)`). A removal whose record fails to commit still frees the name, since nothing holds the address any more; that step is then drawn as not done, naming why, and the result says the name is free. On its page, **Abandon…** is the preview: the same steps run as a dry run, which reads (NetBox, the repository, the credential store, the host-key record and every network's inventory) and removes nothing. **Abandon <device>** confirms that preview: holding the device, it takes the dry run again and, if any step's words changed (NetBox gained an object, the intent is already gone), refuses naming both and removes nothing; otherwise it runs the steps and records the run. The pending row is flagged overdue after a day and stale after a week; one boot takes minutes.

### Static: a person applies it {#static-a-person-applies-it}

![Static address: the tool renders the bootstrap config on request and records the download as a reveal; a person carries the file to the device and applies it; the device boots with its address; Verify reaches it.](diagrams/onboard-static.svg)

What the tool does: it renders the configuration when asked, and nothing else. What you do: everything that gets it onto the device.

1. **Get it.** On the device's pending page, press **Get the bootstrap config…** (it calls `POST /v2/onboard/<device>/bootstrap`), and it is drawn in place to copy. It is a reveal: it needs a verified person, it is recorded in the reveal record with who and when, and a refusal returns no configuration at all. The review screen's copy is not usable: its password is a placeholder.
2. **Apply it.** Either paste it at the device's console in configuration mode (`configure terminal`, then the file's lines; it ends with `end`), or place it where the device loads its startup configuration from and boot the device. Nothing in the onboarding code reads or expects a particular startup path; where the file goes is yours.
3. **The SSH key and the account line follow the device's environment.** The bootstrap generates the device's SSH key itself, unless the device's environment brings SSH up: an `ip ssh` or `crypto key` line among the environment's own lines in its NetBox config context. The account line uses `secret 0`, unless the environment injects its own account (a `username` line there), when it uses `password 0`, because a device given an account ahead of its startup file refuses a `secret` for the same account. Verify's rotation replaces it with a hashed secret. With no NetBox, or no config context, the bootstrap generates the key and uses `secret 0`.

Where the credential travels: from the tool to your browser in the reveal, then however you move it. It is in the clear in that copy and at the console. What limits it: it is one-time, it is replaced by Verify's rotation (after which the copy no longer signs in and the reveal refuses, because the staged credential is gone), and every reveal is recorded. Keep the file as you would a password until Verify has run.

Timing, measured on an emulated IOS-XE router: it takes about six and a half minutes to finish booting. If Verify says the device did not answer, its result names the likely causes in order, with the console command that settles each.

### DHCP reservation: an address, not a configuration {#dhcp-reservation-an-address-not-a-configuration}

![DHCP reservation: a person adds a reservation in Kea and carries the bootstrap config to the device, exactly as for static; Kea gives the device its address when it boots; Verify asks Kea for the lease to find it.](diagrams/onboard-dhcp.svg)

What the tool does: at the plan, it asks Kea whether the MAC you gave has a host reservation and refuses without one (a dynamic lease would move at a renewal and the record would not). At Verify, it asks Kea for the device's LEASE and uses that address, refusing if the lease and the reservation disagree. It writes nothing to Kea on this path.

What you do: add the reservation in Kea's own configuration before the plan, and then deliver the bootstrap configuration exactly as for static (Get the bootstrap config… on its pending page, a recorded reveal; paste it or place it as the startup configuration; the bootstrap generates its SSH key unless its NetBox environment brings SSH up). The bootstrap configures the management interface with `ip address dhcp`.

The reservation gives the device an address on its reserved MAC, and nothing more: no configuration file and no server option. On this path the configuration still arrives by your hand. The credential travels and is protected as for static. If Verify cannot find the device, it says whether Kea has no lease for the MAC yet (the device has not booted or not asked) or a lease that differs from the reservation, naming both.

### ZTP on IOS-XE: the tool serves it {#ztp-on-ios-xe-the-tool-serves-it}

![ZTP on IOS-XE: Create writes a Kea reservation carrying the server's address (option 66) and the file name (option 67); the configless device takes its address, asks the tool's TFTP responder for that file, and the responder renders it on request, records a reveal row, and serves it only to the reserved address; Verify then reaches the device.](diagrams/onboard-ztp-iosxe.svg)

What the tool does, all of it:

1. **The reservation** (Create's `reserve` step). Kea gives the reserved MAC its address, its hostname (option 12), the TFTP server's address (option 66: the tool's own address on that subnet, derived from the host's interfaces, never configured) and the file to fetch (option 67: `<device>.cfg`). Both server options are always sent. No route, resolver or static-route option (3, 6, 33, 121) may reach the device, at any level of Kea's configuration, and the plan also checks that nothing on the segment answers DNS: a configless IOS-XE device that can resolve names calls Cisco's servers before it looks for anything local.
2. **The responder.** A small TFTP server in the tool, started by a systemd socket on UDP port 69 bound to the ZTP interface, so it holds no privilege. Read requests only, octet mode, 512-byte blocks. For each request it decides, from what it reads at that moment: the requester must hold a reservation the tool wrote, in any network's ZTP reservations (each read from the fragment its network's Kea owner writes, as on the DHCP page; a fragment that cannot be read is named in the refusal); the file asked for must be the one that reservation names; the device must be pending and onboarded as ZTP, in the network whose Kea holds that reservation. ZTP is IPv4 only: Kea reserves through DHCPv4, so a request from an IPv6 address is refused and the refusal says so. It then renders the configuration from committed intent and the staged credential, writes a reveal row (the requester, the device and the hash of what it serves, never the text) and only then sends it. Anything else is refused with a TFTP error, and the refusal is recorded too. Nothing is written to disk but those rows. HTTP is not used anywhere on this path.
3. **The bootstrap** for ZTP generates the device's SSH key and uses the `secret 0` account form, because no day-0 configuration from anywhere else will.

What a person does: cable and power the device with no startup configuration, and touch nothing at its console. Any input there (even `enable`) stops discovery. With no startup configuration, IOS-XE runs AutoInstall: it takes the lease, asks the server in option 66 for the file in option 67, and applies it. It does not save it; Verify's persist step does.

An emulated IOS-XE image that boots a day-0 configuration of its own never asks: it must be made to boot configless first. A real IOS-XE device with no configuration asks by itself.

Where the credential travels: over TFTP, which is cleartext, on the ZTP segment, inside the configuration. What limits it: only the reserved address is served, only the named file, only while the device is pending; every fetch is a reveal row written before anything is sent; the configuration is rendered per request and never stored; and the credential is one-time, replaced by Verify's rotation, after which the responder has nothing to serve (the device is no longer pending and the staged credential is gone).

Timing, measured on IOS-XE 17.6: the fetch is a few blocks and takes seconds; AutoInstall retries roughly every 8 seconds and gives up after about 2.5 minutes and nine unanswered requests, after which the device needs a reload to ask again. So a responder that is down or refusing during that window fails the onboarding rather than delaying it.

Mercury's onboarding-progress reader reads each stage below again every 10 seconds and the pending page draws itself again when one moves. After `fetched_not_reached` it probes the reserved address (ICMP, then a TCP connection to port 22; nothing sent, no login), and the page says **Answering: ready to Verify** once the device accepts. The stop rule is the operator's: no fetch 15 minutes after boot: stop; the page marks it 15 minutes after the Create with no fetch of its own.

How to tell where it is: the device's pending page shows its ZTP stage, each from its own source (Kea's running configuration, Kea's lease table, the responder's reveal rows):

- `reservation_missing`: the reservation is not in Kea's running configuration; abandon and re-create;
- `reserved_not_leased`: no lease yet: the device has not booted or not asked;
- `leased_not_fetched`: it has an address and has not asked for its file;
- `asked_not_served`: it asked and was refused, with how many times and the last reason; act within AutoInstall's window or reload it;
- `fetched_not_reached`: it fetched its file; Verify must now reach it over SSH.

Only requests recorded from this onboarding's Create on count. A name abandoned and created again is a new onboarding with a new credential, and the first one's fetch is still in the responder's record under the same name; it is not this one's.

The responder has its own row on Needs attention (`nmas-ztp-responder`): its socket down, not installed, or failing since it last started.

### ZTP behind a relay {#ztp-behind-a-relay}

Built, and not yet proven on a device (registered as C1346: a relayed AutoInstall has never run here). A device whose subnet this host is not on asks through a router's `ip helper-address`, which forwards its request to Kea. What changes from the above:

1. **The subnet.** Add it on DHCP › Subnets with **Add a subnet…**, ticking **For ZTP onboarding** ([how it works](dhcp-subnet#add-for-ztp)). Its reservations are then onboarding's alone, and the DHCP page refuses one there. A ZTP address in a subnet this host is not on and that was not added this way is refused at the review, naming this way ("DHCP › Add a subnet, For ZTP onboarding").
2. **The relay must be a device Mercury manages**, with exactly one interface on the prefix in its committed intent and an `ip helper-address` there. A relay the tool does not manage is refused: its helper address, its own address and its configuration are what the checks read, and none of them is typed in.
3. **The server address** (option 66) is the relay's helper address that is one of this host's own addresses on an interface Kea listens on, where the forwarded request arrives. None, or more than one, is refused naming the relay's helper addresses and this host's.
4. **Gateway** must be the relay's own address on the device's subnet: the device's configuration needs a route back to this host, and the relay is its one neighbour toward it. Blank is refused naming the relay's address ("no gateway given: … Set Gateway to the relay's own address"); another address is refused naming both.
5. **Route option (3)**, the select under Gateway, drawn whenever Address from is ZTP: **None (D4)**, the default, sends no route option, as on the directly attached subnet. **The relay's own address** sends option 3 as the relay's own address and nothing else, for an AutoInstall that needs a route to fetch its file from off its subnet; whether IOS-XE needs it is what the relayed proof measures. It is never a DNS server. Chosen for a device on a subnet this host is on, the review refuses it ("option 3 (routers) is offered only on a relayed ZTP subnet, as the relay's own address"). The choice is part of the reviewed plan: the review's address line says "offering option 3 (routers) <address>, the relay's own address" or "with no option 3", a different choice is a different plan, and the reservation and `dhcp/ztp-reservations.yml` (its `router`) both hold it. At Create the reserve step reads the relay again, and a relay whose address moved since the review is refused ("the plan offers option 3 …, and the relay's own address is now …: preview again"), writing nothing.
6. **The checks** at the review, at Create and on Needs attention (one row per relayed subnet, `ztp-posture:subnet-<id>`): the subnet holds none of this host's addresses (one that does is not relayed, and is refused); Kea's relay address for the subnet is the relay's own address in intent; this host has a route to the device's address from the server address; no resolver or other route option reaches the reservation; and nothing answers DNS for that segment. The relay forwards a device's broadcast DNS query to each of its helper addresses, so each is asked a DNS query from this host, and the relay's committed golden must not run `ip dns server`. A helper address that answers, or a relay that runs a DNS server, fails the check; one that could not be asked, or a golden that cannot be read, is unknown, never a pass.
7. **The firewall.** The host's firewall admits TFTP from the management subnet only. A host step admits it from each relayed ZTP subnet (`scripts/host-steps/c1346-ztp-relayed-firewall.sh`, the operator's to run) and records what the firewall showed; Needs attention's `ztp-firewall` row names a relayed subnet that record does not admit, and says when the record is absent or cannot be read.

The responder serves a relayed device as it serves any other: the request arrives from the reserved address, routed through the relay, and is decided by the same rules. ZTP is IPv4 only, behind a relay too: an IPv6 subnet cannot be added for ZTP, and an IPv6 address is refused by name.

### ZTP on classic IOS: not built {#ztp-on-classic-ios-not-built}

Not built or measured (registered as C1348 and C1349). The plan does not refuse it, and nothing in the ZTP path checks the platform, but whether a classic IOS device AutoInstalls by the option-67 file name has never been measured, so do not rely on it: onboard classic IOS with a static address or a DHCP reservation. The responder serves only the file the reservation names, so AutoInstall's default file names (such as `network-confg`, `router-confg` or `<hostname>-confg`) are never served.

## Phase two: Verify

Verify reaches the device, which is the only proof its address and management interface are right. It is a preview and a confirm (on the device's pending page, **Verify…** then **Verify <device>**), because it sends a program, and it needs a verified person.

**The preview** reaches the device and sends nothing. Read: the device's address (for DHCP and ZTP, the lease Kea holds for its MAC), a check that it answers ICMP or TCP port 22, an SSH login with the staged credential, and its running configuration. It then shows what Verify will send: the removal of any read-write SNMP community the device arrived with (and the read-only ones kept), and the network's monitoring profile lines the device lacks, masked. You confirm its fingerprint, which binds the configuration read, the profile program and the removal lines.

**The confirm** holds the device for the whole phase and runs, in order:

1. **Verify** (`verify`). Read: the address as in the preview (a DHCP or ZTP lease that disagrees with the reservation is refused, naming both), the ICMP or TCP check, and an SSH login with the credential the tool holds for that address. Sent: nothing. Recorded: for DHCP and ZTP, the discovered address and its prefix on the manifest. Three outcomes, each said: it answered; it answered and refused the credential (so the address and interface are right); it did not answer (with the likely causes, most worth checking first).
2. **Capture** (`capture`). Read: the running configuration, over SSH with the staged credential. Sent: nothing. Recorded: nothing yet: held in memory. If the device or the profile moved since the preview, the fingerprint no longer matches and nothing at all is sent.
3. **Rotate** (`rotate`). Read, Sent and Recorded: as [Rotate a credential](rotate) describes, with three differences: there is no separate confirmation (the step records that it skipped the fingerprint check because there is no window between plan and apply), the new password is recorded in the credential override for the device's address rather than an inventory row (it has none yet), and no golden is written. Its commit carries the intent's secret reference and the manifest entry. On success the staged bootstrap credential is removed.
4. **Remove RW** (`remove_rw`). Read: the capture from step 2. Sent: `no <the line>` for each `snmp-server community … RW` line, verbatim, so the access list or view on it still matches. Recorded: nothing. Nothing to remove is a success.
5. **Profile** (`profile`). Read: the running configuration again, after sending. Sent: the monitoring profile's lines the device lacks, once, with errors read by the deploy's pattern. Recorded: nothing. A line that did not land fails the step. With no preview confirmed, or no profile, nothing is sent and the step says why.
6. **Persist** (`persist`). Read: `show startup-config` and the running `username` lines. Sent: `write memory`. Recorded: a persist row where job health reads it. The device's own save only (see [Persist](persist)); it writes no startup file anywhere but on the device. A read-back that does not carry the rotated credential stops the run: the running configuration holds the only working credential, so do not reload the device.
7. **Golden** (`golden`). Read: the running configuration once more. Sent: nothing. Recorded: the device's FIRST golden, one commit as you with `Source: onboarding`. It is read after the cleanup and the rotation, so the repository's first record holds neither the read-write community nor the bootstrap credential.
8. **NetBox** (`netbox`). Read: NetBox, through the import. Sent: nothing to the device. Recorded: the device's objects in NetBox, imported from the first golden, with this Verify as the authority, and its NetBox id on the manifest. A device onboarded from a Planned record updates that record, found by the id the plan recorded (never by name and site, which would miss a record in another site), and never writes its status, role, platform, site or tags; a record renamed or deleted since the plan is refused, naming it, and nothing is written. The step fails, and the device stays pending, when NetBox is not configured, when its writes are switched off, or when the import reports the device failed; writes that did not land are named.
9. **Promote** (`promote`). Read: the credential override, which now holds the rotated password. Sent: nothing. Recorded: the device's inventory row (address, driver, account, the rotated password encrypted, its identity, platform and role; on a NetBox-sourced list the row arrives with the next refresh instead), and the manifest marks it verified. It refuses to store the bootstrap credential as the device's password. Only now is the device onboarded. Then the manifest's two changes since the golden's commit, the NetBox id and the verified time, are committed together as you, `Source: onboarding` (`onboarding: <device> verified and recorded in NetBox`), so the list's repository is left clean and the next operation that needs it clean (Retire) is not refused. A manifest that did not change makes no commit. A commit that fails undoes nothing: the step fails and says so, naming git's reason.

Onboarding adds nothing to Oxidized: its step went with Oxidized's retirement (2026-10-08). The first golden's commit is the device's backup.

**The device's SSH host key.** The preview's SSH login is the first time Mercury meets the device, so it keeps the key the device presents, before it signs in, with when and who (see [Re-key](rekey#every-session)): from then on every session to that address compares the key and refuses a different one with nothing sent, the bootstrap credential included. A device whose address already has a key on record must answer with that key, or the preview and Verify are refused naming both keys. Retiring a device, or abandoning its onboarding, forgets the key kept for its address as one of its steps, named in its preview with the key's fingerprint: the key moves into the record's history with when, who and why, so the next device onboarded at that address is a first contact. The key is kept, and the preview says so naming both, only while another device in any network has the same address: it is still that device's key.

A step that fails stops the run and names every step that did not run; the device stays pending, and Verify can run again. Every Verify and Abandon is recorded beside the list's repository (`onboarding_runs.jsonl`, or the records database once that store is moved; see [The records database](records-database#move)) and read back on the device's pending page (its last run) and on History.

## Then

First boot carries the management plane only: its hostname, the one-time account, the domain,
the address the tool reaches it on and SSH. Nothing else is sent at first boot, so no other
secret travels by TFTP. Its pending page shows five steps: identity, first-boot config,
confirmed, waiting (with Kea's and the config server's view of it) and arrival.

Verify's result then names the next step. When its committed intent says more than it runs,
**Deploy its intent…** opens its Deploy: an ordinary deploy, the exact program previewed and
masked, confirmed by its hash, verified and rolled back on failure. When its intent is still
only its first-boot config, nothing can be compared with it yet: the result says "Intent can't
be checked yet: <device>'s intent is its first-boot config. Next: Actions › Seed intent…", with
the comparison's own words behind **Details**, and the device page's Intent check says the same.
Run [Seed intent](seed) from what it runs, then deploy. When its intent is full and the device
already runs all of it, there is nothing to deploy: write what it should run first (Intent ›
Edit, bulk intent for many). From then on, change it by deploys.

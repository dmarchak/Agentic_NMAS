The controller app deploy: board for the operator's sign-off (C2678)

P6's screen (the SDN platform design revision 6, section 10 H; revision 7). Deploying a network's managed controller apps to its controller is one operation on the device-change lifecycle: preview (the plan: files and hashes, conformance, the drop-in before and after, the restart and the switches that reconnect, each bound with its provenance), confirm by the plan's hash as a verified person, apply holding the controller (stage over SFTP as the deploy account, the request, the one command, the outcome), verify (the post-check), rollback on a miss (Mercury's second request), and record (the receipt, History).

Twelve artboards at 1440 wide: A SDN › Apps at rest; B an app's page; C the plan; D plans refused, and a plan that changes nothing; E running; F results: deployed, and failed partway; G results: the post-check missed; H the receipt and History; I Needs attention; J drift; K the manual page; L phone width. Then the decisions, each a question with a recommendation. Yellow dashed notes are the board's annotations, not part of the screen; a note marked Built today names where the code on main differs from what is drawn. Every other link and control is one the built screen will have.

Not signed. A proposal: the Apps boards are the operator's (decision 11, 2026-11-06). It is a new file rather than artboards appended to docs/boards/lab9-sdn.html, because that board's artboard B draws "apps" as flows Mercury installs (DNS filtering and DHCP steering), the model revision 6's decision 3 replaced with controller apps; and because its D1 to D8 are settled, so an unsigned proposal inside it would blur which artboards are signed. This board supersedes lab9-sdn's artboard B's framing of the Apps tab; B's steering cards become each app's page (artboard B here).

A · SDN › Apps: the network's controller and its managed apps, at rest: a new tab on the SDN page. The controller card leads (what the controller runs, as read, against Mercury's record); then the apps, grouped by what to do. One controller per network today; a network with several draws one card each, folded but for the one with something to do.

Deploy apps to an SDN controller

A network's controller apps (Ryu apps such as of_versions, switch_quirks and dns_blacklist) come from the network's code repository. Only a Published version deploys, byte for byte the version reviewed. Every deploy sends the whole set the controller will run and restarts the controller, so every switch drops and reconnects; Mercury checks they all come back and, if they don't, puts the set before back. You start it on SDN › Apps.

The steps

  1. Plan. Mercury reads the controller (its unit's User and command line, the app folder's owner and mode, its drop-in), stages each app's folder from git's blobs at its pinned commit and checks its hash, checks conformance for every expected switch, and renders the drop-in the apply script will write. A refusal names what it compared, and nothing is staged.
  2. Confirm. You confirm as yourself; the button names the work. At the confirm the plan is made again, holding the controller: a different hash sends nothing and says what moved.
  3. Window. A planned-restart window is recorded for the controller, its switches expected to drop, before anything is sent.
  4. Stage. The files go over SFTP as the deploy account, only into /opt/ryu-apps/<app>/<version>/; the request is written last.
  5. The one command. sudo -n /usr/local/sbin/mercury-ryu-apply, with no argument: the only thing the deploy account may run as root. The script checks the request and every folder's hash again, writes the drop-in (keeping the one before as mercury.conf.prev), restarts the unit and judges it by identity: a new MainPID, active, User ryu.
  6. Post-check. Every expected switch, link and app's /health, within a bound shown with where it comes from.
  7. Rollback. On a miss, Mercury applies the request the controller ran before, the same way, and checks again. The script never rolls back by itself. With no request before, nothing is rolled back, and the receipt names the break-glass.
  8. Record. The receipt, on History.

What each result means

  • Deployed: everything came back, each switch with its time. Rolled back: it missed, and the set before is back. Rollback failed: it missed and so did the rollback. Failed: it stopped partway, the receipt says what landed; nothing is ever deleted on the controller. Unknown: the command was sent and its outcome not read.

The bounds

Both are about 2.5 times a measured time. Until they are measured, each is marked a placeholder wherever it appears, and the receipt keeps that.

Decisions for the operator: each a question, with the board's recommendation; none is taken. K1 to K9 shape the screen; the findings the board raised (F1 to F7) are listed after them for the register.

K1 · Where the screen lives

  1. Recommended: a new SDN › Apps tab per network, the controller card first and each app's page under it (artboards A and B); SDN › Controllers' row for the controller links to it. Revision 6's section 16a already places H's apps on SDN › Apps; the deploy is about the controller's whole set, and apps are what people choose.
  2. On SDN › Controllers, as a section of the controller's row: the connection view and the deploy view in one table, the apps a level further down.

K2 · What Mercury's record of the controller's set is (what drift compares with, and what a miss rolls back to)

  1. Recommended: the last deploy's receipt whose outcome left the controller running its request (deployed, or rolled back to the one before), kept in Mercury's records with the other receipts. No separate "enabled" file: choosing a version and deploying it is one decision. The rollback target is the request before, shown in the plan and bound into its hash.
  2. An apps/enabled.yml per network, as revision 6 had it: a second record to keep in step, and in the configuration repository, which revision 7 (11c.4) keeps apps' tools from reading, or in the code repository, which Mercury never writes.

K3 · A miss with no previous request (the first deploy)

  1. Recommended for S3: the plan says before the confirm that there is no rollback target, and the confirm names it ("… with no rollback", artboard D); a miss's receipt names mercury.conf.prev as the break-glass, which is a root step on the host, listed as LABOUR in docs/MANUAL_STEPS.md with its finding.
  2. After S3: a second request kind the apply script accepts, "put the drop-in before back", so even a first deploy's miss is rolled back by Mercury. It changes the root script, a host-installed file, and its host step.

K4 · Redeploying the set the controller already runs

  1. Recommended: offered, as a secondary "Redeploy the same set and restart ctl-1…" on a plan that changes nothing (artboard D), because drift repair needs it (a drop-in edited on the host); the preview says no file or line changes and the restart still happens.
  2. Refused as "nothing to deploy": drift whose cause is the drop-in alone could then be repaired only by deploying another version and back.

K5 · The bounds on placeholders at S3

  1. Recommended: S3's deploys run on the placeholders if S1 has not replaced them, each marked "placeholder" in the plan, the result and the receipt; S3's first receipt records the unit's time to active and each switch's reconnect after the restart, which are C2687's and C2674's measurements, and the bounds take them after.
  2. No deploy to a real controller until both bounds are measured: S3's step 2 waits on a restart timed by hand outside Mercury.

K6 · What the post-check expects when something is already wrong before the deploy

  1. Recommended: it expects every switch and link NetBox names and every enabled app's /health, as built; the plan draws what is already missing or failing beside it (artboard C's question) and the confirm names it ("… expecting dns_blacklist's /health to recover"), so a miss that was there before is never a surprise.
  2. It expects back only what answered at plan time, naming the rest as not expected: a deploy can then pass with a switch down, and the deploy never fixes what it cannot see.

K7 · An unknown outcome (the command sent, no outcome of this run read)

  1. Recommended: Mercury reads the outcome and the unit once more after the bound; still unknown, the receipt says "Unknown", the window runs to its end, a Needs attention row (Unknown) offers "Read the outcome again", and a rollback is offered as a preview, never run by itself.
  2. Roll back at once: a second restart when the first may have succeeded.

K8 · Each switch's time

  1. Recommended: counted from the apply script's restart (the post-check's own time plus the unit's time to active), drawn "back N s after the restart", because that is the reconnect the bound and S3's PASS line are about.
  2. Counted from the post-check's first read, as built, and labelled so.

K9 · How an app's compiled config reaches the controller

  1. Recommended: a config file per app staged beside its version, /opt/ryu-apps/<app>/<version>.config.json, its hash in the request (the request gains config_sha256), shown in the plan and checked by the script; the Published folder's hash stays the reviewed code's. For what an app needs at start (switch_quirks' tables).
  2. Pushed over the app's REST policy endpoint after the restart (revision 6's "policy as data"): no change to the script, but the app runs without its config until the push, and the post-check would judge it before.
  3. Both: start-time config by (1), runtime policy (dns_blacklist's verdict service) by (2).

Findings in the built code (for the register; the board draws the intended behaviour, each marked "Built today")

  1. F1 (B): post_check.deploy ends at "apply failed" with no rollback even when the script's outcome says the new drop-in was written and the unit restarted (step daemon-reload, restart or wait): what landed stays.
  2. F2 (B): channel.plan carries neither the rollback target nor the post-check's expected links and apps, and its hash body (request, drop-in after, unit, controller, switches) covers neither.
  3. F3 (B): the request and the staged folder have no place for an app's compiled config (decision K9).
  4. F4 (B): post_check.wait's per-switch times count from its first read, after the script's wait for the unit, so they understate each reconnect by the unit's time to active.
  5. F5 (C): the receipt's outcome is "rollback failed" when no rollback was tried (no previous request).
  6. F6 (B): conformance.check's checked rows lack the profile entry and the switch's own versions, so a passing row cannot draw both operands.
  7. F7 (B): channel.window_seconds is 2 × (UP_BOUND_S + the post-check's bound), but the transport waits 2.5 × UP_BOUND_S for the command and staging is uncounted, so a rollback can outlast the window.
